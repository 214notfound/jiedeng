# 第一部分　模块分工：谁负责谁

## 1.1 一句话概括

**"剧情"不是写出来的代码，而是声明成数据、由引擎在运行时算出来的。**

`game-line` 定义骨架（顺序与条件），三个能力域提供血肉（玩家看到什么），中间靠 `handoff` 这条"订单"连接。

## 1.4 连接方式：`handoff`

骨架与模块之间**只有一条连接线**：字符串 ID。

**骨架侧**（例：`game-line/data/prologue.js`）

```js
{
  id: "prologue-briefing",
  capability: "conversation",        // 谁来做
  targetId: "prologue-briefing",     // 做哪一段  ←── 连接键
  npcIds: ["companion-x"],
  goalIds: ["surface-task-known"],   // 做到什么算完成
  startWhen: { allFacts: ["prologue-wake-context-known"] }
}
```

**模块侧**（例：`exploration/conversation/data/conversations.js`）

```js
{
  node: "prologue-wake",                          // ←── 挂在哪个 Node
  target: "prologue-briefing",                    // ←── 连接键，必须一字不差
  type: "conversation",
  npc: "companion-x",
  actions: [{
    id: "surface-briefing",
    label: "与小周交谈",
    facts: ["surface-investigation-task-known"],  // ←── 对应 goalIds 覆盖的事实
    text: "【小周】我是公司的安全联络员。……"
  }]
}
```

三类 `capability` 的差异：

| capability | 命令类型 | 回传事件 | 数据文件 | `targetId` 是否校验存在 |
|---|---|---|---|---|
| `exploration` | `REQUEST_EXPLORATION` | `OBJECT_INVESTIGATED` | `exploration/data/exploration.js` | ❌ **不校验** |
| `conversation` | `REQUEST_CONVERSATION` | `NPC_TALK_PROGRESS` / `NPC_TALKED` | `exploration/conversation/data/conversations.js` | ❌ **不校验** |
| `minigame` | `REQUEST_MINIGAME` | `MAP_PUZZLE_COMPLETED` / `MINIGAME_RESOLVED` | `minigames/**` | ✅ 查 `story-registry.js` 的 `minigames` 白名单 |

## 1.6 ⚠️ 三个陷阱（改之前必读）

### 陷阱 1：`shopkeeper-inquiry` 的显示文本来自 `conversations-v2.js`，不是 `conversations.js`

`exploration/conversation/game/conversation.js:133` 的逻辑是：

```js
const v2Conversation = V2_CONVERSATIONS[action.id];
if (v2Conversation) { /* 用 V2 版本，逐行显示 */ }
// 否则回退到 conversations.js 里的单段 action.text
```

`conversations-v2.js` 目前只定义了 `shopkeeper-inquiry` 一个键。**改小卖部老板的台词，必须改 `conversations-v2.js`**；`conversations.js:34` 里那一大段是死文本，改了不会生效。

### 陷阱 2：`week-one-end` 的展示文本被 V3 整体替换过

`game-line/data/v3/registry-extension.js:127` 用 `replaceStoryNode` 把 `week-one-end` 从 revision 1 升到 2，其中 `presentations`、`transitions`、`terminal`、`endingId` 是**整体替换**的。

因此 `game-line/data/old-house.js:248-267` 里那两段旁白（"更紧迫的问题仍是……" / "而另一个问题已经无法忽视……"）是**死文本**。玩家实际看到的是 registry-extension 里的新文案。

### 陷阱 3：`action.description` 不会被渲染

`reading-contract.js` 的 `normalizeActions` 只保留 `actionId` / `label` / `actionType` 三个字段，`assets/js/core/` 全目录没有任何地方读 `description`。

因此 `v3/finale.js` 中 `evidence-disposition` 三个选项的 `description`（"销毁四组证据，什么都不留。"等）**玩家看不到**。想让玩家看到说明，必须写进 `presentation.blocks`。

### 附加提醒

- **改 `targetId` / `target` / `npcId` 必须两侧同步改**。`conversation` 和 `exploration` 的 `targetId` 只校验格式（kebab-case），不校验存在性，敲错一个字控制台依然打印 `validation: "passed"`，只有玩家点了那个 NPC 才会发现什么都没发生。
- **纯文案改动不要动 `revision`**。`checkpoint` 里存了 `nodeId + nodeRevision`，改了 revision 会让所有停在这一幕的存档失效（除非同时在 `checkpointMigrations` 里补一条迁移）。
- **改完看控制台第一行**：`[white-lamp:story] 剧情引擎启动 { ..., validation: "passed" }`。是 `passed` 才算安全。

# 第二部分　剧情全序列

## 阅读说明

- **顺序**：按正常推进顺序排列。标有「**可任意顺序**」的小节，内部条目玩家可以按任意次序完成。
- **来源标注**：每段文本后用 `〔来源〕` 标出所在文件。
- **方括号 = 本文档的标注，不是文本内容**：
  - `[旁白]` / `[系统]` = `game-line` 展示块的 `blockType`（`narration` / `system`）。**代码里没有这两个前缀**，是本文档为了让"这是旁白还是系统提示"一目了然而加的。
  - `[按钮]` = 玩家可点击的操作；`[标签]` = 场景中的任务标签；`[小游戏]` = 小游戏界面文案。
- **【方头括号】 = 文本内容本身，必须原样保留**：对话模块（`conversations*.js`）的 `text` 字段里，`【小周】` `【老板】` `【旁白】` 等是**玩家实际看到的内容**，写入数据时不能丢。本文档逐字照抄。
- **死文本**：折叠在 `<details>` 里的内容已确认**不会显示**（被后来的版本整体替换），保留在此仅供对照。看到它就说明该处有两份文案，改错了不会生效。
- **不列入的内容**：各 Node 的 `intent` 字段与各里程碑的 `intent` 字段是**设计意图**（写给开发者看的），玩家看不到，因此本文档不逐条列出。
- **⚠️ V3 探索文本的类型规则**：`exploration/data/exploration.js` 中的 V3 任务由 `v3Task()` 生成，它的规则是 **"最后一行是 `[系统]`，其余全部是 `[旁白]`"**——**不是**"归档结论行是 `[系统]`"。改动这些任务的 `blocks` 时请注意：新增一行会改变最后一行是谁。
