# V2 剧情接口确认

## 1. 基本逻辑

运行时，剧情模块只和晨菲负责的 `game-flow` 通信：


页面或业务模块 $\longrightarrow$ game-flow $\longrightarrow {\color{red}{\text{story engine}}} \longrightarrow$ game-flow $\longrightarrow$ 页面或业务模块


- 只有 `game-flow` 调用剧情入口。
- 冰轩和正松只需在开发时用真实样例确认字段；正式运行仍由 `game-flow` 转发。

## 2. 剧情模块唯一公开入口

```js
window.WhiteLamp.story.enterStory(request)
```

输入是 `StoryRequest`，输出是完整的 `StoryResponse`。现有详细规则继续使用 [《剧情模块接口约定》](./剧情模块接口约定.md)，

### 输入

| `input.type` | 用途 | 必要内容 |
|---|---|---|
| `new-game` | 新游戏 | 空事实、`storyCheckpoint: null` |
| `resume` | 读档恢复 | 已校验的事实和检查点 |
| `story-action` | 提交剧情操作 | `actionId` |
| `external-event` | 接收探索、对话或小游戏结果 | 完整外部事件 |

### 输出

```js
{
  contractVersion,
  requestId,
  status,
  commit,
  presentation,
  commands,
  notifications,
  error
}
```

| 字段 | 谁使用 | 用途 |
|---|---|---|
| `status` | 晨菲 | 决定进入阅读、探索、小游戏、结束或错误状态 |
| `commit` | 晨菲 | 提交检查点和状态事件 |
| `presentation` | 冰轩，经 `game-flow` 转发 | 显示剧情文字和合法操作 |
| `commands` | 正松等业务模块，经 `game-flow` 转发 | 执行探索、对话或小游戏 |
| `notifications` | 全局、成就、日志 | 接收剧情完成通知 |
| `error` | 晨菲和页面 | 保留原状态并提示玩家 |


## 3. 字段说明

`StoryRequest` 顶层有 **5 个字段**；`StoryResponse` 顶层固定有 **8 个字段**。

### 3.1 输入 `StoryRequest`

| 字段 | 内容类型 | 要求 | 用途 |
|---|---|---|---|
| `contractVersion` | 字符串 | 必填，当前固定为 `"1.0"` | 确认双方使用同一版接口 |
| `requestId` | 非空字符串 | 必填，同一次请求保持不变 | 对应请求与响应，并防止重复结算 |
| `source` | 非空字符串 | 必填，正式全局当前传 `"game-shell"` | 记录请求来自哪里，不参与剧情判断 |
| `input` | 对象 | 必填 | 说明这次为什么进入剧情 |
| `context` | 对象 | 必填 | 提供当前事实和剧情检查点；剧情只读，不修改原对象 |

#### 3.1.1`input` 对象

`input.type` 决定同一对象中还要带什么字段：

| `input.type` | 其他字段 | 内容类型 | 要求 |
|---|---|---|---|
| `new-game` | 无 | — | `facts` 必须为空，`storyCheckpoint` 必须为 `null` |
| `resume` | 无 | — | 必须提供非空且有效的 `storyCheckpoint` |
| `story-action` | `actionId` | 非空字符串 | 必须是当前 Node 正在提供的合法 action |
| `external-event` | `event` | 对象 | 必须是当前等待命令对应的外部结果 |

#### 3.1.2`context` 对象

| 字段 | 内容类型 | 要求 | 用途 |
|---|---|---|---|
| `facts` | 字符串列表 | 必填，不能重复；新游戏必须为空 | 状态模块已经确认的剧情事实 |
| `storyCheckpoint` | 对象或 `null` | 必填；只有新游戏使用 `null` | 指出当前 Node、完成进度和等待命令 |

`storyCheckpoint` 非空时包含：

| 字段 | 内容类型 | 要求 | 用途 |
|---|---|---|---|
| `nodeId` | 字符串 | 必须是已经登记的 Node ID | 当前剧情 Node |
| `nodeRevision` | 正整数 | 必须与当前 Node 版本一致 | 防止旧存档误读新剧情 |
| `completedMilestoneIds` | 字符串列表 | 只能写当前 Node 已完成的里程碑，不能重复 | 记录当前 Node 内的稳定进度 |
| `completedNodeIds` | 字符串列表 | 只能写已登记 Node，不能重复 | 记录本局已经完成的 Node |
| `completedStageIds` | 字符串列表 | 只能写已登记阶段，不能重复 | 记录已经完成的剧情阶段 |
| `pendingCommands` | 对象列表 | `commandId` 不能重复，且命令必须属于当前 Node | 保存仍在等待的探索、对话或小游戏 |

`pendingCommands[]` 中每项固定有 3 个字段：

| 字段 | 内容类型 | 用途 |
|---|---|---|
| `commandId` | 字符串 | 当前等待命令的稳定 ID |
| `commandType` | 字符串枚举 | `REQUEST_EXPLORATION`、`REQUEST_CONVERSATION` 或 `REQUEST_MINIGAME` |
| `targetId` | 字符串 | 命令指向的探索、对话或小游戏 ID |

#### `external-event` 的 `event` 对象

| 字段 | 内容类型 | 要求 |
|---|---|---|
| `eventId` | 非空字符串 | 一次外部结果一个稳定 ID，用于去重 |
| `eventType` | 非空字符串 | 必须与当前等待命令的类型匹配 |
| `source` | 非空字符串 | 当前允许 `exploration`、`conversation` 或 `minigame`，并要与命令来源一致 |
| `causedByCommandId` | 非空字符串 | 当前代码要求必填，必须指向 `pendingCommands` 中的命令 |
| `resultFactIds` | 字符串列表 | 不能重复；所列事实必须已由状态模块提交到 `context.facts` |
| `payload` | 对象 | 具体字段由 `eventType` 决定 |

`event.payload` 的实际结构：

| `eventType` | `source` | `payload` 必要字段 |
|---|---|---|
| `OBJECT_INVESTIGATED` | `exploration` | `objectId`：非空字符串 |
| `NPC_TALK_PROGRESS` | `conversation` | `conversationId`、`npcId`：非空字符串 |
| `NPC_TALKED` | `conversation` | `conversationId`、`npcId`：非空字符串 |
| `MAP_PUZZLE_COMPLETED` | `minigame` | `puzzleId`：必须等于当前小游戏目标 ID |
| `EXTERNAL_INTERACTION_CANCELLED` | 与当前命令一致 | `targetId`：必须等于当前命令目标 ID |
| `EXTERNAL_INTERACTION_FAILED` | 与当前命令一致 | `targetId`、`errorCode`：非空字符串 |

注意：旧接口说明曾提到独立调查可以不带 `causedByCommandId`，但当前 `story-request.js` 会把它判为字段不完整。V2 按当前代码执行，所有进入剧情的外部事件都必须带 `causedByCommandId`。

### 3.2 输出 `StoryResponse`

| 字段 | 内容类型 | 要求和用途 |
|---|---|---|
| `contractVersion` | 字符串 | 固定为当前接口版本 `"1.0"` |
| `requestId` | 字符串 | 正常情况下原样返回输入的 `requestId` |
| `status` | 字符串枚举 | `ready`、`waiting-external`、`ended` 或 `error` |
| `commit` | 对象或 `null` | 成功时有提交内容；错误时必须为 `null` |
| `presentation` | 对象或 `null` | 本次要显示的剧情内容；没有展示时为 `null` |
| `commands` | 对象列表 | 本次完整的等待命令；没有时为空列表 |
| `notifications` | 对象列表 | 本次剧情通知；没有时为空列表 |
| `error` | 对象或 `null` | 成功时为 `null`；错误时给出原因和恢复办法 |

#### `commit` 对象

| 字段 | 内容类型 | 用途 |
|---|---|---|
| `checkpoint` | 对象 | 新的剧情检查点，结构与输入的 `storyCheckpoint` 相同 |
| `events` | 对象列表 | 需要状态模块一次性提交的状态事件 |

`events[]` 中每项固定有：

| 字段 | 内容类型 | 用途 |
|---|---|---|
| `eventId` | 字符串 | 本次状态事件 ID |
| `eventType` | 字符串枚举 | 状态模块要执行的事件类型 |
| `onceKey` | 字符串 | 防止同一剧情效果重复结算 |
| `payload` | 对象 | 事件携带的具体目标 |

| `eventType` | `payload` 字段 | 含义 |
|---|---|---|
| `STORY_FACT_RECORDED` | `factId` | 记录剧情自产生的事实 |
| `CHOICE_MADE` | `choiceId` | 记录剧情选择；当前 V1 没有正式 choice 数据 |
| `ITEM_ACQUIRED` | `itemId` | 发放物品 |
| `CLUE_RECORDED` | `clueId` | 记录线索 |
| `LOCATION_UNLOCKED` | `locationId` | 解锁地点 |

#### `presentation` 对象

| 字段 | 内容类型 | 用途 |
|---|---|---|
| `presentationId` | 字符串 | 本次展示的稳定 ID，用于防止重复渲染 |
| `sceneId` | 字符串 | 剧情场景 ID，不是图片路径或 DOM ID |
| `blocks` | 对象列表 | 按数组顺序显示的文本块 |
| `actions` | 对象列表 | 当前允许提交的剧情操作 |

`blocks[]` 中每项包含：

| 字段 | 内容类型 | 要求 |
|---|---|---|
| `blockId` | 字符串 | 本次展示内的文本块 ID |
| `blockType` | 字符串枚举 | 当前只允许 `narration` 或 `system` |
| `text` | 非空字符串 | 玩家实际看到的正文 |

`actions[]` 中每项包含：

| 字段 | 内容类型 | 要求 |
|---|---|---|
| `actionId` | 字符串 | 回传给剧情的真实操作 ID，不能用按钮文字代替 |
| `label` | 非空字符串 | 玩家看到的按钮文字 |
| `actionType` | 字符串枚举 | `advance` 或 `choice` |

#### `commands` 列表

每个命令都有 `commandId`、`commandType` 和 `payload`。`payload` 随命令类型变化：

| `commandType` | `payload` 字段 | 内容 |
|---|---|---|
| `REQUEST_EXPLORATION` | `explorationId`、`goals` | 要进行的探索及完成目标 |
| `REQUEST_CONVERSATION` | `conversationId`、`npcIds`、`goals` | 要进行的对话、参与人物及完成目标 |
| `REQUEST_MINIGAME` | `minigameId`、`successFactId` | 要启动的小游戏及成功事实 |

其中 `npcIds` 是字符串列表，`goals` 是对象列表；每个目标包含 `goalId` 和给业务模块阅读的 `description`。

`commands` 与 `commit.checkpoint.pendingCommands` 必须使用同一组 `commandId`。检查点只保存命令摘要，`commands` 才带业务模块执行所需的完整 `payload`。

#### `notifications` 列表

每项固定包含 `eventId`、`eventType` 和 `payload`：

| `eventType` | `payload` 字段 | 含义 |
|---|---|---|
| `STORY_NODE_ENTERED` | `nodeId`、`nodeRevision` | 进入新 Node |
| `STORY_MILESTONE_REACHED` | `nodeId`、`milestoneId` | 达成里程碑 |
| `STORY_NODE_COMPLETED` | `nodeId` | 完成 Node |
| `STORY_STAGE_COMPLETED` | `stageId` | 完成剧情阶段 |
| `STORY_ENDED` | `endingId` | 剧情到达终点 |

#### `error` 对象

| 字段 | 内容类型 | 用途 |
|---|---|---|
| `errorCode` | 字符串 | 给程序判断错误种类 |
| `userMessage` | 字符串 | 可以显示给玩家的中文提示 |
| `developerMessage` | 字符串 | 给开发者定位问题，只进控制台 |
| `recoveryActions` | 字符串列表 | 建议全局提供的恢复操作，如重试、返回菜单 |

## 4. 状态表

### 4.1 输入类型与检查点状态

| `input.type` | `context.facts` | `context.storyCheckpoint` | 剧情收到后做什么 |
|---|---|---|---|
| `new-game` | 必须是空列表 | 必须为 `null` | 创建 `prologue-wake` 初始检查点 |
| `resume` | 当前存档事实 | 必须是有效对象 | 从当前 Node、里程碑和等待命令恢复 |
| `story-action` | 当前正式事实 | 必须是有效对象 | 校验并执行当前 Node 的 `actionId` |
| `external-event` | 必须已包含事件声明的结果事实 | 必须是有效对象且含对应等待命令 | 校验外部结果，完成目标后移除命令并尝试推进 |

### 4.2 输出状态与字段组合

| `status` | `commit` | `presentation` | `commands` | `notifications` | `error` | 全局处理 |
|---|---|---|---|---|---|---|
| `ready` | 对象 | 必须是对象 | 可以为空，也可以有命令 | 列表 | `null` | 提交成功后进入阅读状态 |
| `waiting-external` | 对象 | 当前引擎实现为 `null` | 至少一条 | 列表 | `null` | 按命令进入或保持探索，必要时开放小游戏入口 |
| `ended` | 对象 | 可以是对象或 `null`；当前实现返回 `null` | 必须为空列表 | 必须包含 `STORY_ENDED` | `null` | 显示结束状态，不再推进 |
| `error` | 必须为 `null` | 必须为 `null` | 必须为空列表 | 必须为空列表 | 必须是对象 | 保留原状态，显示 `userMessage`，控制台记录开发信息 |

成功响应的处理顺序固定为：先校验响应，再提交 `commit`；提交成功后发布完整命令和通知，最后更新展示。提交失败时不能显示新剧情。

## 5. 真实样例

这里不手写运行结果。每份样例都应保存一对数据：实际送入 `enterStory()` 的完整 `StoryRequest`，以及同一次调用返回的完整 `StoryResponse`。

### 必须补充

1. `new-game → ready`：新游戏进入 `prologue-wake`。覆盖空检查点、初始 presentation 和 `STORY_NODE_ENTERED`。
2. `story-action → waiting-external`：提交 `confirm-wake-context`。覆盖 `actionId`、状态事件、里程碑和 `REQUEST_CONVERSATION`。
3. `external-event → waiting-external`：完成开场对话并进入 `prologue-belongings`。覆盖外部事件和 `REQUEST_EXPLORATION`。
4. `resume → waiting-external`：在任一等待命令处保存并恢复。确认命令 ID、目标和完整 payload 能重建。
5. `waiting-external + REQUEST_MINIGAME`：进入地图拼图等待状态。覆盖小游戏命令结构。
6. `external-event → ready`：完成地图拼图。覆盖 `system` 文本块、发放物品和解锁地点事件。
7. `story-action → ended`：在 `week-one-end` 提交结束操作。覆盖空命令和 `STORY_ENDED`。
8. 非法 `story-action → error`：提交当前 Node 不允许的 `actionId`。覆盖完整错误对象，并确认剧情没有推进。

### 建议补充

1. `EXTERNAL_INTERACTION_CANCELLED`：确认不产生事实，原等待命令仍可继续。
2. `EXTERNAL_INTERACTION_FAILED`：确认返回错误，不把失败当成完成。
3. 同一 `requestId` 或外部 `eventId` 重复提交：确认全局去重，不重复发奖或推进。

当前 V1 正式数据没有 `choice` action，因此无法提供 V1 真实 choice 样例。这个能力由现有自动化测试验证即可，不要为了凑样例新增剧情选择。
