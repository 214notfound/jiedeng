# 剧情模块接入说明

## 1. 当前交付

剧情模块默认仍加载 V1 三阶段、11 个运行 Node；追加 V3 脚本后，扩展为 28 个运行 Node、四段后续阶段和五个结局。本轮不包含 `game.html` 展示层，也不代替状态、存档、探索、对话、小游戏或成就模块。

V1 不实现旧需求中的“相信/怀疑小周”选项；这是主动取消的需求，不是遗漏。引擎仍支持未来数据声明 `choice` 和 `CHOICE_MADE`。

人物显示名映射固定为：`companion-x` → 小周，旧编辑代号 A → 陈晋年，旧编辑代号 B → 王阙。`key-a`、`burned-work-id` 等技术 ID 不改名。工作证前期只显示王姓，村民称“王工程师”，不得提前显示王阙全名。

## 2. 浏览器加载顺序

全局页面必须按以下顺序加载脚本：

```html
<script src="../assets/js/game-line/data/story-registry.js"></script>
<script src="../assets/js/game-line/data/prologue.js"></script>
<script src="../assets/js/game-line/data/village.js"></script>
<script src="../assets/js/game-line/data/old-house.js"></script>
<script src="../assets/js/game-line/game/story-validator.js"></script>
<script src="../assets/js/game-line/game/story-runtime.js"></script>
<script src="../assets/js/game-line/game/story-request.js"></script>
<script src="../assets/js/game-line/game/story-engine.js"></script>
```

当前页面继续使用上面的 V1 顺序。联调完整 V3 时，须在三个 V1 数据文件之后、引擎文件之前按以下顺序插入：

```html
<script src="../assets/js/game-line/data/v3/registry-extension.js"></script>
<script src="../assets/js/game-line/data/v3/outer-investigation.js"></script>
<script src="../assets/js/game-line/data/v3/identity-reconstruction.js"></script>
<script src="../assets/js/game-line/data/v3/mine-return.js"></script>
<script src="../assets/js/game-line/data/v3/finale.js"></script>
```

完整顺序为“V1 registry/data → V3 registry 扩展 → 四个 V3 阶段数据 → validator/runtime/request/engine”。扩展版本、重复 ID、未知引用或 Node 数据错误都会显式停止加载或使入口返回错误。

加载成功后唯一公开入口为：

```js
window.WhiteLamp.story.enterStory(request)
```

启动时控制台会打印模块版本、接口版本、起止 Node、Node 数量和预检结果。预检失败时入口只返回 `STORY_INVALID_NODE_DATA`，不会跳过坏数据继续游戏。

## 3. 全局协调器的固定流程

1. 外部模块把事件交给全局状态模块；状态模块校验来源、`eventId` 和 `causedByCommandId` 后提交事实。
2. 协调器用提交后的事实和当前剧情检查点调用 `enterStory()`。
3. 协调器把响应中的 `commit.checkpoint` 与 `commit.events` 作为一次事务提交。
4. 提交失败时保持旧检查点，不分发成功通知、命令或新展示。
5. 提交成功后分发 `notifications`、`commands` 和 `presentation`。

剧情内核无状态，不使用 DOM 或 `localStorage`。协调器负责持久化去重 `requestId` 和外部 `eventId`；状态模块负责按 `onceKey` 防止重复发奖。

新游戏的剧情事实必须为空、检查点必须为 `null`。初始背包由全局初始状态工厂放入 `burned-work-id` 和 `blue-glass-bead`，不能让剧情内核私自补写。

状态模块提交以下事件后，还要产生对应事实：

| 状态事件 | 派生事实 |
| --- | --- |
| `ITEM_ACQUIRED key-a` | `key-a-acquired` |
| `ITEM_ACQUIRED map-fragment-1/2/3` | 对应的 `map-fragment-1/2/3-acquired` |
| `ITEM_ACQUIRED restored-village-map` | `restored-village-map-acquired` |
| `LOCATION_UNLOCKED old-house` | `old-house-unlocked` |

状态模块不得根据外部事件自行选择下一 Node，也不得直接修改剧情检查点内部字段。

## 4. 文案修改规则

叙述和系统提示位于三个阶段数据文件的 `presentations[].blocks`。修改措辞、增加或删减文本块、调整分页或改变对话轮数，不需要修改 Node ID 或 `revision`。

实现层在最低 Node 格式上增加两个内部字段：

| 字段 | 固定内容 |
| --- | --- |
| `presentations[]` | `id`、`when`、`sceneId`、`blocks`、`actionIds` |
| `blocks[]` | `id`、`blockType`、`text`；类型只允许 `narration` 或 `system` |
| `actions[]` | `id`、`label`、`actionType`、`availableWhen`、`effect` |

同一状态最多命中一个 presentation；同时命中多个时会返回 `STORY_INVALID_NODE_DATA`，不会按数组顺序猜测。`presentation` 和 `block` 的 ID 用于渲染去重，不进入剧情检查点。

人物对白由对话模块根据剧情命令中的 `goals` 编排；剧情模块不检查句数。只有修改里程碑、完成条件、事实含义或转移关系时才增加 `revision`。V3 已登记 `week-one-end@1 → @2` 迁移；其他未知 revision 明确报错。

## 5. V3 外部 handoff

- 探索、对话仍使用 `REQUEST_EXPLORATION`、`REQUEST_CONVERSATION`。对话模块可自由扩展内部列表，只需围绕 `npcIds` 和 `goals` 回报 `NPC_TALK_PROGRESS` 或 `NPC_TALKED`。
- 新小游戏命令为 `REQUEST_MINIGAME { minigameId, gameStyle, allowedResultFactIds }`。三个目标分别是 `haunting-network-puzzle`（`puzzle`）、`mine-route-puzzle`（`puzzle`）、`x-showdown-chase`（`chase`）。
- 新小游戏完成事件为 `MINIGAME_RESOLVED`。payload 必须带匹配的 `minigameId`，`resultFactIds` 必须且只能包含一个允许结果；追逐结果是 `x-showdown-survived` 或 `x-showdown-lost`。
- `EXTERNAL_INTERACTION_FAILED` 只表示技术故障，不能产生结果事实，也不能触发《封井之人》。旧 `map-puzzle` 的命令载荷和 `MAP_PUZZLE_COMPLETED` 事件保持不变。

| handoff target | 命令 | 需要回报的事实 |
| --- | --- | --- |
| `investigate-gorge-and-grave` | `REQUEST_EXPLORATION` | `a-gorge-thread-complete` |
| `investigate-project-records` | `REQUEST_EXPLORATION` | `project-record-thread-complete` |
| `investigate-su-trail` | `REQUEST_EXPLORATION` | `su-thread-complete` |
| `investigate-white-lamp-mail` | `REQUEST_EXPLORATION` | `white-lamp-first-thread-complete` |
| `haunting-network-puzzle` | `REQUEST_MINIGAME` | `haunting-is-engineered` |
| `investigate-control-room` | `REQUEST_EXPLORATION` | `protagonist-is-b-known`、`intimidation-plan-authorship` |
| `investigate-old-clinic` | `REQUEST_EXPLORATION` | `a-b-identity-chain-complete`、`a-left-clinic-with-sister-known` |
| `investigate-father-and-company` | `REQUEST_EXPLORATION` | `old-accident-coverup-proven`、`father-full-role-known`、`company-succession-chain`、`b-prior-mine-ignorance-established` |

选择 action 仍由剧情内核产生 `CHOICE_MADE`，状态层按登记表派生事实：`hand-over-evidence` / `refuse-handover` 对应交付或拒绝；追逐生还后，`destroy-all-evidence`、`publish-curated-evidence`、`publish-full-evidence` 三选一。外部模块只提交选择事件，不指定下一 Node。
