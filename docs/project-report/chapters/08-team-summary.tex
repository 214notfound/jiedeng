\chapter{小组总结}

9 月 2 日，五名成员各自提出选题方向，逐一陈述并互相质询，当天确定最终方案，完成仓库初始化。9 月 3 日确定开发方式为需求驱动的 subPR 闭环。此后四个版本按同一条链路推进，中途未更换做法。

从立项到 9 月 20 日交付，代码规模从空目录增长到 92 个 JavaScript 文件、15{,}677 行，12 个样式表、3{,}802 行，以及 35 个测试文件、6{,}122 行。本章按版本复盘开发过程，归纳期间反复出现的技术问题与协作机制，并整理团队在方法和判断上的变化。

\section{项目开发全景复盘}

\subsection{V1：链路打通（9.3--9.8）}

V1 的目标是打通一条完整的游玩链路，使玩家可以从封面走到第一周的结尾。

分工按模块划分。于知让负责账户与剧情，罗晨菲负责全局与存档，高冰轩负责小游戏，卢正松负责探索与成就，杨梦负责入口页与介绍页。本代交付 13 个页面、一套存档体系、前置剧情，以及第一个地图小游戏。

第一版在浏览器上跑通后，提交记录留下两条问题：可玩性不高，文字与背景颜色对比度不足；各板块已经串联，但浏览器端操作路径繁琐。这两条构成 V2 的改进输入。

V1 另有两项事项影响了后续版本。状态模块最初记录了剧情引擎已经拒绝的事件，该问题在 V3 被写成接口契约；团队接口约定草案在本代末被整体废弃，改为按模块拆分的多份文档。

\subsection{V2：模块边界成文（9.7--9.11）}

V2 的主要变化在分工方式。文档从「谁做什么」改为「谁拥有哪些文件、不负责什么」。

五名成员各承担一个模块。罗晨菲负责全局状态与正式集成，高冰轩负责游戏页面与统一阅读组件，于知让负责剧情展示与剧情回归，卢正松负责点击式探索、NPC 对话、背包与成就，杨梦负责场景美术与视觉验收。

每个模块章节的开头都列有「不修改」的范围。罗晨菲不编写剧情内容、热点数据、对话内容、拼图规则和场景美术；卢正松不修改剧情 Node、全局状态、正式存档和 \texttt{game.html} 结构；杨梦不修改热点坐标、业务状态、剧情内容和页面切换代码。

本代交付中段剧情、新增小游戏、线索与成就扩展，以及历史存档兼容。边界成文之后，跨模块问题有了固定的归属对象，该机制的运行情况见 8.3.3。

\subsection{V3：接口冻结（9.9--9.15）}

V3 是三周中记录最完整的一代，产出 28 个剧情 Node 与五个结局。接口契约列出探索、对话、小游戏三类共 14 条交接指令，每条注明发送方、接收方与携带字段。

本代分工收缩为三个方向。高冰轩负责游戏页面与全局状态，卢正松负责点击式探索与整体功能集成，杨梦负责场景美术与剧情回归。于知让承担本代需求文档的编写，罗晨菲完成全局模块的对接；此后两人同期参加数学建模竞赛，未列入本代的模块分工表。

\section{技术难点与解决}

\subsection{状态记录的信任边界}

V1 时期的提交记录写明了问题：状态模块会记录剧情引擎已经拒绝的事件。该问题的后果是错误事实进入存档，此后所有读取存档做出的判断都以错误事实为基础。

V3 将其固化为规则。\texttt{OBJECT\_INVESTIGATED} 是探索模块调查完对象后唯一可发送的事件，携带对象 ID 与结果事实 ID，正式状态事件由剧情模块在 commit 中产生。接口补充文档的表述为：「状态模块只接收剧情运行时生成的正式状态提交，不由探索模块直接写 \texttt{STORY\_FACT\_RECORDED}」。

V3 实施规格另外区分了简写与正式实现。契约文档中「探索模块直接回报状态事件」属于交接层的简写，正式运行时不得采用。该区分的目的是避免后续接手者依照简写实现代码。

这条规则的作用是把存档中的事实限定为经过剧情引擎校验的事实。

\subsection{界面切换规则的合并冲突}

V2 中期，两位负责人分别编写了一份界面切换规则文档。两份文档各自成立，合并时发现八处冲突，合并提交逐条记录了冲突与决策，其中三条如下。

\begin{itemize}
  \item \textbf{界面的并行显示。} 一份规定同一时刻只能显示一个状态，另一份允许阅读与背包同时显示。最终确定为一个当前状态加一个锁定背景。
  \item \textbf{拼图的返回位置。} 一方主张固定返回探索界面，另一方主张返回阅读界面。最终确定为返回打开拼图之前的界面，由状态字段记录。
  \item \textbf{状态字段的归属。} 确定由控制器记录返回状态，发起方只发送打开详情的请求。
\end{itemize}

八处冲突在同一次合并中全部定案，终稿标注合并日期，此后所有页面切换以该文档为准。冲突集中在文档合并阶段暴露并解决，未进入开发阶段。

\subsection{测试通过与正式可玩的差距}

V3 有一条链路，28 个剧情 Node 全部通过测试。同期检查报告指出，14 条 V3 业务交接指令尚无一条在正式页面完成实现，并明确「不能把 28 个 Node 测试通过等同于 V3 正式可玩」。

报告列出 B01 至 B10 共十项阻断，逐项记录当前证据与建议负责人，其中三项为：

\begin{itemize}
  \item B01：公共事实表只登记 V1 事实。
  \item B04：存档校验的白名单来自该事实表，V3 事实无法写入。
  \item B06：探索校验将节点版本号硬编码为 1。
\end{itemize}

报告同时规定关闸顺序，B01、B02、B04、B05、B06、B07、B08 必须先关闭；B03 与 B09 可延后，但必须在指定小游戏开工之前完成。

同一批问题中另有一例。玩家进入外围调查节点并读完介绍后，页面停留在阅读层，四个场景入口均不可见。调查确认探索模块已提供四个入口，断点在全局页面状态。修复方式是在阅读器上增加阅读完成回调，由阅读器在最后一个真实阅读块结束时触发；文档同时注明不得伪造完成，也不得以关闭操作替代阅读完成。

单元测试覆盖的是模块内部逻辑，正式可玩还取决于模块在运行时的接入情况。

\subsection{存档迁移的处理原则}

V3 将某节点的版本号由 1 升至 2，节点 ID 不变，语义由游戏终点变为老宅结束、完整调查开始。针对三类旧存档的处理如下。

\begin{itemize}
  \item 停留在该节点且未提交确认：保留节点 ID，版本号更新为 2。
  \item 已完成该节点：连同事实与完成记录迁移至下一节点。
  \item 节点、阶段或事实缺失：返回版本不兼容错误，不做补齐。
\end{itemize}

第三类处理确定了后续所有迁移的原则，即不做推测性补齐。相关规定还包括旧存档事实不得自动改名重用，正式迁移规则由剧情与存档负责人提供。

\section{协作机制与认知}

\subsection{模块边界的书面化}

V2 之后，每份需求文档的模块章节开头均列出「不修改」范围。V3 接口契约进一步明确 14 条交接指令的发送方、接收方与字段，并附注区分对话内容的归属。

边界书面化的效果是改动一个模块不需要通知其他模块。V3 实施规格另有一条约束：探索模块不得根据按钮文字、场景名称或当前 URL 推测对象 ID。该约束的作用是避免通过间接信号建立隐式依赖。

\subsection{冲突处理的组合原则}

V2 至 V3 期间，仓库中留有三份组合审阅文档，对应三组并行提交的合并请求。第一份审阅文档规定，冲突解决必须组合双方语句，不得整段保留一方。

该规定的必要性有两处实例。

\begin{itemize}
  \item 某份提交删除的样式表中包含仍然有效的声明，仅保留一侧会导致详情页长内容无法滚动。该提交本身无问题，它删除的是重复声明，合并后才发现其中混有一条有效声明。
  \item 某条分支为所有新获得物品自动打开详情页。合并后，玩家取得旧钥匙时会弹出物品卡片，中断正在进行的阅读流程。修正方式是将自动打开标记限定在三张地图碎片。
\end{itemize}

这两处问题在任一分支上单独存在时都不会出现，只在合并时出现。

\subsection{问题的归属与回退}

V2 需求文档确定了问题按归属回退的机制：页面结构、焦点与响应式问题回到高冰轩；剧情文本与动作含义回到于知让；热点、调查、对话、背包与成就规则回到卢正松；场景构图与素材回到杨梦。

V3 将该职责交由卢正松承担，并要求先判断问题属于单个模块还是两个以上模块的交接处。

提交记录中有对应实例，包括「修复卢正松提出的两个bug」「修改杨梦所说的坐标问题」「修复对话读完无法推进的问题」。三个问题由不同成员报出，由归属责任人修复并复测。

场景审查记录了一例完整的修正过程。陈家老宅的正式门开图片重画后，四个热点的原有坐标不再对应，四项坐标逐一对齐；测试同时锁定四个坐标互不重叠，且均在合法百分比范围内，防止后续回退到旧位置。

\subsection{文档冲突的处理}

三周内废弃两份文档，处理方式一致。

V1 的团队接口约定草案被整体替换，文件头注明该文件已废弃、仅保留用于追溯历史讨论，正文注明剧情模块以哪两份文档为准。

V3 需求文档更换版本，旧版改名为历史版，说明文档标注其仅用于追溯、不作为当前实现依据。新版增加一节，规定 V3 功能开发必须建立在最终 V2 基线之上，不得从尚未包含完整 V2 的旧分支开始批量开发。

两份文档均予保留，保留的目的是记录当时的判断依据。

\section{项目开发认知}

\subsection{可玩性问题的处理}

V1 跑通后的两条问题记录之一，是文字与背景颜色对比度不足。该问题没有通过调整个别色值解决。V2 建立 \texttt{tokens.css}，将全站色值与间距收为一份变量表，其余样式表只引用变量名，基调修改一次即可覆盖全站。

体验类问题比功能类问题暴露更晚。自动打开物品详情的改动在功能上没有缺陷，只在玩家实际取得旧钥匙时才会发现问题。

\subsection{可维护性问题的处理}

V4 改写剧情文本时出现三类问题，均不属于代码错误。

\begin{itemize}
  \item 修改的文件不是实际生效的文件。某 NPC 的显示文本来自较新的数据文件，另一文件中的同名内容早已失效。
  \item 节点被上层替换，原文件中的两段旁白同样失效。
  \item 选项的 \texttt{description} 字段在归一化阶段被丢弃，写入后玩家不可见。
\end{itemize}

三类问题的共同点是代码逻辑正确、测试通过，但修改的位置不在生效路径上。剧情数据在 V1 已确定数据与引擎分离的组织方式，实际执行中仍出现了重复数据。

同期完成一项清理，测试中硬编码的块数、条数、末条 ID 全部改为从数据推导。

V4 修复网络小游戏时，提交标题为使其可评审、可诊断。该小游戏此前没有供他人评审与定位问题的入口，本次补充三个评审工具文件与两组交互测试。

\subsection{验收标准的建立}

V3 收尾阶段的进度文档，第一节标题为「尚不能宣称最终交付完成」，列出待完成项：真实浏览器桌面与移动端视觉、键盘焦点、五条结局逐条截图、音频配置。

同一文档的「不得误做」一节列有六条，其中一条为不因素材齐全而宣称功能已经可玩。

发布验收方案将缺陷分为两级。无法进入正式游戏、流程不能推进、存档损坏、资源大面积缺失属于阻断级，须修复后重跑全部门禁；其余属于严重级，须修复后重跑相关链路与全量测试。方案另规定合入后必须从发布分支重新运行门禁，不得复用功能分支上的旧结果。

验收标准在开工阶段即已确定，版本的完成判断由此有据可依。

\section{总结与不足}

从 9 月 2 日立项到 9 月 20 日交付，主线累计 229 次提交，73 个合并请求，其中 68 个已合入。流程中有三项做法保证了推进效率：版本从需求评审开始，不从任务分配开始；模块边界写入文档，不依赖口头约定；问题有明确归属与回退路径。

不足有四项。

一是 V1 的需求文档没有分工记录，五名成员姓名均未出现，第一代的贡献只能通过提交记录回溯。

二是素材类工作的排期。V4 先完成视频，随后发现祠堂与结局的场景图需要重画才能衔接，产生一次可避免的返工。

三是音频交付时间偏晚。V3 收尾时，资源对照表中音频一栏仍为「尚未交付」，跨页面续播的修复完成时也没有配套素材，直到 V4 才接入 5 段背景音乐与 7 处音效。

四是测试断言中一度存在硬编码数值。该问题在同一轮内修复，但反映出编写测试时求快的倾向。

后续版本的改进方向有两项：分工记录从第一代起写全；将相互依赖的素材工作安排在同一阶段完成。
