# 剧情模块接口约定

- **版本：** V1.0
- **适用范围：** 本项目 V1 及后续剧情内容
- **依据：** `需求文档v1.md`、`剧情Node推进.md`、`team-interface-contract-v1.md`
- **文档状态：** V1.0 双重审核完成，待团队确认冻结

## 1. 本文解决什么问题

本文只约定模块边界和交接格式，回答四个问题：

1. 哪些事情由剧情模块决定，哪些事情不归剧情模块；
2. 其他模块在什么时机、通过什么入口把结果交给剧情模块；
3. 剧情模块向界面、状态、探索、对话、小游戏和成就模块返回什么；
4. 一个可进入、可推进、可保存的剧情 Node 最少要写哪些内容。

本文不规定对白要写几句、文字怎样逐字出现、热点放在哪里、拼图怎样拖动，也不规定 DOM、CSS 或动画实现。

## 2. 已确定且不得模糊处理的原则

### 2.1 Node 表达剧情目标

Node 记录这一段剧情希望发生什么、玩家应当知道什么、满足什么条件才算完成。它不等于一句话、一个对话框、一次点击或一个页面。

一个 Node 可以：

- 一次展示完；
- 分成多段叙述；
- 经过若干轮人物交谈；
- 等待调查、选择或小游戏完成后继续；
- 同时包含必须完成和可以跳过的剧情里程碑。

禁止用“显示第 3 句话”“点击 5 次后完成”“`stepIndex === 4`”一类界面步骤作为 Node 的完成条件。

### 2.2 剧情只规定对话目标

人物对话的边界固定如下：

- 剧情模块规定参与者、谈话目的、玩家最终需要得知的事实，以及哪些事实出现后谈话对剧情来说已经完成；
- 探索/对话模块负责具体台词、谈话轮数、话题展开方式、按钮和版面；
- 剧情模块不读取“当前是第几句”，也不要求对话必须在固定轮数内完成；
- 对话模块不能自行决定下一剧情 Node。它只能报告谈话取得了什么结果，再由剧情模块判断是否推进。

例如 `剧情Node推进.md` 的 V11“继续闲聊得知旧事故表层版本”，可以聊两轮，也可以聊五轮。只要对话模块最终报告 `old-accident-public-version-known`，剧情模块就认为对应里程碑已经到达。

### 2.3 状态和存档只有一个写入口

- 剧情模块不直接修改全局游戏状态；
- 剧情模块不直接读写 `localStorage`、`sessionStorage` 或存档文件；
- 剧情模块只返回待提交的状态事件；
- 全局状态模块负责校验并一次性提交这些事件；
- 存档模块只保存已经提交成功的状态。

剧情返回“希望记录什么”，状态模块决定“是否成功写入”。写入失败时，不得继续显示已经推进后的内容。

### 2.4 外部模块只报告事实

探索、对话和小游戏模块不得传入 `nextNodeId`，也不得直接修改 `currentNodeId`。它们只报告已经发生的事情，例如：

- 调查了 `old-photograph`；
- 和老人谈话后得知旧事故的公开说法；
- `map-puzzle` 已完成；
- 某次外部交互被取消或执行失败。

下一段去哪里，只由剧情模块根据当前 Node、已记录事实和转移条件决定。

## 3. 职责边界

| 事项 | 剧情模块 | 其他模块 |
| --- | --- | --- |
| Node、阶段和转移关系 | 定义并维护 | 不得直接改当前 Node |
| 玩家此时应该知道什么 | 定义剧情里程碑 | 对话/探索按目标组织实际内容 |
| 人物具体说什么、聊几轮 | 只给目标和必要背景 | 对话模块负责 |
| 调查热点怎样操作 | 只说明需要取得的结果 | 探索模块负责 |
| 小游戏规则和成功判定 | 只请求启动，并声明剧情等待的成功事实 | 小游戏模块负责 |
| 选项代表的剧情含义 | 定义选项 ID、可见文案和剧情影响 | 界面负责展示并回传选项 ID |
| 当前状态和状态变更 | 读取只读上下文，返回待提交事件 | 全局状态模块统一提交 |
| 保存与恢复 | 定义剧情检查点的最低结构 | 存档模块校验、读写和报错 |
| 背包内容 | 可以请求发放物品 | 背包只读取已提交状态并展示 |
| 成就 | 发出节点、阶段等剧情通知 | 成就模块自行判断和解锁 |
| DOM、CSS、动画、音频 | 不负责 | 游戏壳、视觉或音频模块负责 |
| 错误处理 | 返回明确错误，不猜测推进 | 游戏壳显示错误，控制台保留技术细节 |

### 3.1 唯一实际调用者

生产代码中，只有游戏流程协调器可以调用剧情入口。页面按钮、对话、探索和小游戏先把事件交给协调器，由协调器按下面的顺序处理：

1. 把外部事件交给全局状态模块，校验事件来源、`eventId` 和等待中的 `commandId` 后再提交；
2. 状态提交成功后，生成剧情只读上下文；
3. 调用统一剧情入口；
4. 提交剧情返回的状态事件和检查点；
5. 提交成功后，再分发剧情命令、通知并更新界面。

任何一步失败都在当前检查点停止。不能一边报错，一边假装剧情已经成功推进。

## 4. 进入剧情的统一入口

逻辑接口固定为：

```js
enterStory(request): StoryResponse
```

这里约定的是输入输出结构，不限制它最终写成普通函数、类方法还是 ES Module 导出函数。

### 4.1 `StoryRequest`

```js
{
  contractVersion: "1.0",
  requestId: "req-0001",
  source: "game-shell",
  input: {
    type: "new-game"
  },
  context: {
    facts: [],
    storyCheckpoint: null
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `contractVersion` | 是 | 本接口版本，V1 固定为 `1.0` |
| `requestId` | 是 | 本次调用的唯一 ID，用于防止重复结算 |
| `source` | 是 | 发起来源的模块 ID，仅用于追踪问题，不参与剧情分支判断 |
| `input` | 是 | 本次进入剧情的原因 |
| `context.facts` | 是 | 全局状态模块生成的只读事实列表 |
| `context.storyCheckpoint` | 是 | 新游戏为 `null`；其他情况为已校验的剧情检查点 |

剧情模块不得修改传入的 `context`。

### 4.2 四种入口原因

`input.type` 只允许下面四种值：

| `input.type` | 谁触发 | 必须携带什么 | 用途 |
| --- | --- | --- | --- |
| `new-game` | 主菜单/游戏壳 | 无附加字段 | 从固定起始 Node 开始新游戏 |
| `resume` | 存档模块经协调器触发 | 检查点已经放在 `context.storyCheckpoint` | 从最近剧情里程碑恢复 |
| `story-action` | 剧情界面 | `actionId` | 玩家点击继续或作出剧情选择 |
| `external-event` | 探索、对话、小游戏经协调器触发 | `event` | 把外部模块已经完成的结果交回剧情 |

`new-game` 必须使用初始状态工厂生成的事实列表，并令 `storyCheckpoint` 为 `null`。`resume`、`story-action` 和 `external-event` 必须带有非空且已经校验的检查点。任何模块都不能借 `new-game` 清空一局仍在使用的状态。

剧情界面提交操作时使用：

```js
{
  type: "story-action",
  actionId: "doubt-x"
}
```

外部模块返回结果时使用：

```js
{
  type: "external-event",
  event: {
    eventId: "evt-0042",
    eventType: "MAP_PUZZLE_COMPLETED",
    source: "minigame",
    causedByCommandId: "cmd-village-map-puzzle",
    resultFactIds: ["map-puzzle-completed"],
    payload: {
      puzzleId: "map-puzzle"
    }
  }
}
```

### 4.3 外部事件的公共格式

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `eventId` | 是 | 外部事件唯一 ID；重复 ID 不得重复结算 |
| `eventType` | 是 | 已登记的事件名称，使用大写下划线格式 |
| `source` | 是 | 实际产生事件的模块 ID |
| `causedByCommandId` | 剧情曾发命令时必填 | 对应剧情此前发出的 `commandId` |
| `resultFactIds` | 是 | 本次交互取得的稳定事实；没有新事实时传空数组 |
| `payload` | 是 | 事件自身数据；没有数据时传空对象 |

V1 剧情必须识别这些外部事件：

| 事件 | 必要 `payload` | 含义 |
| --- | --- | --- |
| `OBJECT_INVESTIGATED` | `objectId` | 某调查对象已完成有效调查，`resultFactIds` 写调查所得事实 |
| `NPC_TALK_PROGRESS` | `conversationId`、`npcId` | 多轮谈话取得了新的剧情进展，但整段谈话尚未结束 |
| `NPC_TALKED` | `conversationId`、`npcId` | 对话模块认定本次谈话已经完成 |
| `MAP_PUZZLE_COMPLETED` | `puzzleId` | 地图小游戏成功完成，`resultFactIds` 至少包含 `map-puzzle-completed` |
| `EXTERNAL_INTERACTION_CANCELLED` | `targetId` | 玩家主动退出对话、探索或小游戏，`resultFactIds` 必须为空 |
| `EXTERNAL_INTERACTION_FAILED` | `targetId`、`errorCode` | 外部模块执行失败，`resultFactIds` 必须为空 |

`resultFactIds` 是外部模块对本次结果的声明，不是绕过状态模块直接写状态。状态模块必须按事实登记表校验“该模块是否有权产生这个事实”，提交成功后再生成新的 `context.facts`。

`NPC_TALK_PROGRESS` 不代表 Node 必然完成。剧情只查看更新后的 `context.facts` 是否满足里程碑条件。普通寒暄没有产生新的稳定事实时，对话模块不必每轮都调用剧情入口。

状态模块发现 `eventId` 已处理时，协调器不得再次调用剧情。非重复事件的 `causedByCommandId` 若不在当前 `pendingCommands` 中，剧情返回 `STORY_STALE_EXTERNAL_EVENT`，不能把过期结果算到当前 Node。没有由剧情发起的独立调查事件可以不带 `causedByCommandId`，但必须在事实登记表中明确允许这种来源。

### 4.4 事实列表

`context.facts` 是状态模块提供给剧情的稳定事实视图，例如：

```js
[
  "key-a-acquired",
  "old-photograph-investigated",
  "old-accident-public-version-known",
  "map-puzzle-completed",
  "trust-x-chosen"
]
```

规则如下：

- 每个事实使用唯一、稳定的 kebab-case ID；
- 事实只表示已经成立的结果，不写界面过程；
- 剧情条件只能读取事实 ID，不能读取别的模块内部字段；
- 事实 ID 发布后不得换名；
- 新增事实必须先登记含义、唯一产生模块和产生时机；
- 外部事件要先由状态模块提交，再把更新后的事实列表交给剧情。

事实登记表属于全局状态约定。剧情接口至少要求每条登记包含 `factId`、中文含义、`producer` 和产生条件，防止任意模块伪造别人的结果。

`dialogue-line-4-shown`、`button-clicked-3-times`、`puzzle-tile-at-2-1` 都不是合法剧情事实。

## 5. 剧情检查点与读档

### 5.1 最低格式

```js
{
  nodeId: "village-elder-old-accident",
  nodeRevision: 1,
  completedMilestoneIds: [
    "elder-willing-to-talk"
  ],
  completedNodeIds: [
    "village-elder-introduction"
  ],
  completedStageIds: [
    "prologue"
  ],
  pendingCommands: [
    {
      commandId: "cmd-village-elder-old-accident-talk-with-elder",
      commandType: "REQUEST_CONVERSATION",
      targetId: "elder-old-accident"
    }
  ]
}
```

`completedNodeIds` 和 `completedStageIds` 用于阶段进度、成就重算和完成通知去重。`pendingCommands` 没有等待中的外部任务时为空数组。使用数组是为了支持“同时询问三名村民、完成顺序不限”这类并行探索；同一个 `commandId` 在数组中只能出现一次。

`completedMilestoneIds` 只保存当前 Node 的里程碑；进入下一 Node 后重新计算。某个里程碑如果会影响后续分支或成就，必须同时对应一个全局事实，不能指望离开 Node 后继续读取旧的局部里程碑。

| 字段 | 说明 |
| --- | --- |
| `nodeId` | 当前 Node 的稳定运行时 ID |
| `nodeRevision` | 当前 Node 的语义版本 |
| `completedMilestoneIds` | 当前 Node 内已经提交成功的里程碑 |
| `completedNodeIds` | 本局已经完成的 Node，用于去重和重算进度 |
| `completedStageIds` | 本局已经完成的阶段 |
| `pendingCommands` | 尚未成功结束的外部任务；允许多条并存 |

### 5.2 保存粒度

剧情存档只保证回到最近一个已经提交成功的剧情里程碑，不保证回到某句对白、某个字或某次动画的中间位置。读档后允许重放当前里程碑之后的少量内容。

检查点不得保存：

- 对话句子序号；
- 当前打字动画字符位置；
- DOM 元素 ID 或 CSS 类名；
- 某个按钮已经点了几次；
- 小游戏内部棋子或图片坐标。

对话或小游戏中途存档时：

- 剧情检查点只保存尚未结束的 `pendingCommands`；
- 对话/小游戏自己的细节进度由对应模块交给全局状态和存档模块；
- 读档后剧情重新返回原来的 `commandId`，外部模块根据自己的已存状态继续，而不是创建一份新任务。

### 5.3 检查点恢复规则

1. 存档模块先校验存档结构和总 `schemaVersion`；
2. 剧情模块再校验 `nodeId`、`nodeRevision`、里程碑、已完成 Node、已完成阶段和等待命令；
3. 校验通过后，以已完成里程碑为准重建当前 Node；
4. 当前 Node 不存在、版本不兼容或等待命令无法恢复时，返回可见错误；
5. 未经玩家确认，不删除、覆盖或偷偷跳过损坏的存档。

## 6. 剧情向外返回什么

`enterStory()` 每次都返回完整的 `StoryResponse`：

```js
{
  contractVersion: "1.0",
  requestId: "req-0001",
  status: "waiting-external",
  commit: {
    checkpoint: {
      nodeId: "village-elder-old-accident",
      nodeRevision: 1,
      completedMilestoneIds: [],
      completedNodeIds: ["village-elder-introduction"],
      completedStageIds: ["prologue"],
      pendingCommands: [
        {
          commandId: "cmd-village-elder-old-accident-talk-with-elder",
          commandType: "REQUEST_CONVERSATION",
          targetId: "elder-old-accident"
        }
      ]
    },
    events: []
  },
  presentation: null,
  commands: [
    {
      commandId: "cmd-village-elder-old-accident-talk-with-elder",
      commandType: "REQUEST_CONVERSATION",
      payload: {
        conversationId: "elder-old-accident",
        npcIds: ["villager-3"],
        goals: [
          {
            goalId: "public-version-known",
            description: "玩家得知十七年前事故的公开版本"
          }
        ]
      }
    }
  ],
  notifications: [],
  error: null
}
```

| 字段 | 说明 |
| --- | --- |
| `contractVersion` | 与请求一致 |
| `requestId` | 原样返回，便于调用方配对 |
| `status` | `ready`、`waiting-external`、`ended` 或 `error` |
| `commit` | 交给状态模块一次性提交的检查点和状态事件 |
| `presentation` | 剧情模块本次提供的叙述、系统提示和剧情操作；没有则为 `null` |
| `commands` | 提交成功后交给探索、对话或小游戏执行的命令 |
| `notifications` | 提交成功后广播给成就、日志等模块的剧情事实通知 |
| `error` | 正常时为 `null`；失败时包含错误信息和恢复方式 |

四种状态的字段约束如下：

| `status` | `commit` | `presentation` | `commands` | `notifications` | `error` |
| --- | --- | --- | --- | --- | --- |
| `ready` | 必须有 | 必须有 | 可以有 | 可以有 | 必须为 `null` |
| `waiting-external` | 必须有 | 可以为 `null` | 至少有一条等待中的外部命令 | 可以有 | 必须为 `null` |
| `ended` | 必须有 | 可以有结束展示 | 必须为空数组 | 必须包含 `STORY_ENDED` | 必须为 `null` |
| `error` | 必须为 `null` | 必须为 `null` | 必须为空数组 | 必须为空数组 | 必须有 |

`waiting-external` 响应中的 `commands` 必须与 `commit.checkpoint.pendingCommands` 使用同一组 `commandId`。不能出现“已经保存为等待中但没有命令可执行”，也不能发出一条没有写入检查点的外部命令。

### 6.1 提交顺序

协调器必须按固定顺序处理返回值：

1. 校验响应；
2. 把 `commit.checkpoint` 和 `commit.events` 作为一次事务交给状态模块；
3. 提交失败时停在旧检查点，只显示错误；
4. 提交成功后分发 `notifications`；
5. 再执行 `commands` 并显示 `presentation`。

这样可以避免玩家看见“获得地图”或“进入老宅”，实际存档里却没有对应状态。

### 6.2 `presentation`

```js
{
  presentationId: "present-prologue-wake",
  sceneId: "shrine",
  blocks: [
    {
      blockId: "wake-after-rain",
      blockType: "narration",
      text: "暴雨停了。你在祠堂里醒来。"
    },
    {
      blockId: "memory-gap",
      blockType: "narration",
      text: "近期的记忆留下了一段空白。"
    }
  ],
  actions: [
    {
      actionId: "inspect-belongings",
      label: "检查随身物品",
      actionType: "advance"
    }
  ]
}
```

`blocks` 可以有零个、一个或多个。界面可以分页、逐段显示或一次显示，但不得改变顺序和语义。`blocks` 只承载剧情自己提供的叙述和系统提示；人物交谈通过 `REQUEST_CONVERSATION` 交给对话模块，剧情不能在这里硬编码谈话轮数。

界面回传 `actionId`，不能用按钮文字判断逻辑。`blockId` 只用于本次展示去重，不进入剧情存档。

| 字段 | 约定 |
| --- | --- |
| `presentationId` | 本次展示的唯一 ID，用于界面防重复渲染 |
| `sceneId` | 语义场景 ID；不传图片路径、DOM 选择器或坐标 |
| `blocks` | 有序内容数组；`blockType` 只允许 `narration` 或 `system` |
| `actions` | 当前合法剧情操作；`actionType` 只允许 `advance` 或 `choice` |

外部对话的台词和对话内操作由对话模块自己的返回结构负责，不塞进剧情的 `blocks`。

### 6.3 `commit.events`

每个待提交事件使用统一格式：

```js
{
  eventId: "story-evt-0101",
  eventType: "ITEM_ACQUIRED",
  onceKey: "prologue-key-given:item-key-a",
  payload: {
    itemId: "key-a"
  }
}
```

V1 允许剧情请求提交这些状态事件：

| 事件 | 必要 `payload` | 用途 |
| --- | --- | --- |
| `STORY_FACT_RECORDED` | `factId` | 记录只由剧情产生的稳定事实 |
| `CHOICE_MADE` | `choiceId` | 记录玩家已经作出的剧情选择 |
| `ITEM_ACQUIRED` | `itemId` | 请求向背包发放物品 |
| `CLUE_RECORDED` | `clueId` | 请求把已确认线索写入背包或线索记录 |
| `LOCATION_UNLOCKED` | `locationId` | 请求开放新地点 |

`commit.checkpoint` 与这些事件必须一起成功或一起失败。可能重复触发的奖励事件必须带稳定的 `onceKey`，状态模块按 `onceKey` 幂等处理。

里程碑的 `onReach` 用于“完成一部分就要立即结算”的效果，Node 的 `onComplete` 用于整个 Node 首次完成后的效果。例如三名村民可以按任意顺序交谈，每个谈话里程碑的 `onReach` 各自发放一块地图碎片，不必等三人全部谈完。

`onReach.id` 和 `onComplete.id` 都必须稳定。里程碑效果的 `onceKey` 由 `${node.id}:${milestone.id}:${onReach.id}` 生成，Node 完成效果的 `onceKey` 由 `${node.id}:${onComplete.id}` 生成；改文案或读档时不得更换这些去重键。

剧情不得直接返回 `ACHIEVEMENT_UNLOCKED`。成就模块应根据已提交事实或剧情通知自行判定，避免剧情同时承担成就规则。

### 6.4 `commands`

每条命令都包含 `commandId`、`commandType` 和 `payload`。V1 使用三类命令：

| 命令 | 接收模块 | 必要 `payload` | 剧情可以规定 | 剧情不得规定 |
| --- | --- | --- | --- | --- |
| `REQUEST_EXPLORATION` | 探索 | `explorationId`、`goals` | 要调查什么、要取得哪些结果 | 热点坐标、点击次数、界面布局 |
| `REQUEST_CONVERSATION` | 对话 | `conversationId`、`npcIds`、`goals` | 参与者、应传达的事实、完成标准 | 台词、轮数、逐句按钮和排版 |
| `REQUEST_MINIGAME` | 小游戏 | `minigameId`、`successFactId` | 启动哪个小游戏、成功后等待什么事实 | 操作方式、内部关卡步骤和成功算法 |

对话命令示例：

```js
{
  commandId: "cmd-village-elder-old-accident-talk-with-elder",
  commandType: "REQUEST_CONVERSATION",
  payload: {
    conversationId: "elder-old-accident",
    npcIds: ["villager-3"],
    goals: [
      {
        goalId: "elder-willing-to-talk",
        description: "老人逐渐愿意谈十七年前的旧事"
      },
      {
        goalId: "public-version-known",
        description: "玩家得知当年的公开说法是学校后山山体滑坡造成孩子死亡"
      }
    ]
  }
}
```

这里没有台词数量。对话模块可以调整过程，只要返回的事实仍能对应这些目标。

`commandId` 必须稳定。推荐由 Node ID 和 `handoffs.id` 组成，例如 `cmd-village-elder-old-accident-talk-with-elder`。刷新、重试或读档时重发同一任务，仍使用原 ID，不能临时生成新 ID。

收到 `NPC_TALK_PROGRESS` 时，对应命令继续保留在 `pendingCommands`。收到成功完成事件后才移除；收到取消或失败事件时，由剧情返回重试或退出方案，不能自行当作成功。一个 Node 可以同时保留多条命令，因此村口三名村民能够按任意顺序交谈。

“对话模块说完成了”不等于“剧情目标已经完成”。`NPC_TALKED` 到达后，如果更新后的事实仍不满足该 handoff 对应的必要里程碑，剧情返回 `STORY_EXTERNAL_RESULT_INCOMPLETE` 并保留原命令。小游戏和探索结果使用同一规则。

### 6.5 `notifications`

剧情通知表示已经完成并提交成功的事实，只用于旁听，不要求接收方回写剧情：

每条通知固定包含 `eventId`、`eventType` 和 `payload`。`eventId` 用于接收方去重，`eventType` 使用下表名称。

| 通知 | 必要 `payload` | 典型接收者 |
| --- | --- | --- |
| `STORY_NODE_ENTERED` | `nodeId`、`nodeRevision` | 日志、调试工具 |
| `STORY_MILESTONE_REACHED` | `nodeId`、`milestoneId` | 成就、日志 |
| `STORY_NODE_COMPLETED` | `nodeId` | 成就、进度展示 |
| `STORY_STAGE_COMPLETED` | `stageId` | 成就、存档提示 |
| `STORY_ENDED` | `endingId` | 游戏壳、结局页 |

通知不能代替状态。错过通知的模块必须能从全局状态重新计算自己的显示结果。

## 7. 各模块什么时候把什么交给剧情

| 模块 | 交给剧情的时机 | 交付内容 | 剧情返回或通知 |
| --- | --- | --- | --- |
| 主菜单/游戏壳 | 玩家确认新游戏后 | `new-game` 与空检查点 | 起始检查点、首个展示或外部命令 |
| 存档 | 存档完成结构校验后 | `resume`、已校验检查点和事实列表 | 最近里程碑的展示；有等待任务时返回原命令 |
| 剧情界面 | 玩家点击当前合法操作后 | `story-action` 与 `actionId` | 新展示、状态事件、外部命令或下一 Node |
| 探索 | 有效调查完成后 | `OBJECT_INVESTIGATED`；状态已包含调查事实 | 更新里程碑，决定继续等待或推进 |
| 对话 | 获得新的稳定信息，或整段谈话完成后 | `NPC_TALK_PROGRESS` 或 `NPC_TALKED` | 更新里程碑，决定继续等待或推进 |
| 小游戏 | 成功判定完成后 | `MAP_PUZZLE_COMPLETED`；状态已包含成功事实 | 请求发放结果、开放地点并推进剧情 |
| 任一外部交互 | 玩家取消或模块失败后 | 取消/失败事件和明确错误码 | 保持当前 Node，提供重试、退出等合法恢复方式 |
| 全局状态 | 每次进入剧情前 | 只读 `facts` 和检查点 | 接收 `commit`，原子提交或明确拒绝 |
| 背包 | 不直接调用剧情 | 无 | 读取状态事件后的背包数据 |
| 成就 | 不直接调用剧情 | 无 | 监听已提交的剧情通知或从状态重算 |

## 8. 剧情 Node 的最低格式

### 8.1 最低可用结构

```js
{
  id: "village-elder-old-accident",
  sourceRef: "V11",
  stageId: "village",
  revision: 1,
  intent: "通过与老人继续交谈，让玩家得知十七年前事故的公开版本。",
  enterWhen: {
    allFacts: ["village-entered"]
  },
  milestones: [
    {
      id: "elder-willing-to-talk",
      intent: "老人放下戒备，愿意继续谈旧事。",
      satisfiedWhen: {
        allFacts: ["elder-old-topic-opened"]
      }
    },
    {
      id: "public-version-known",
      intent: "玩家得知公开说法是学校后山山体滑坡造成孩子死亡。",
      satisfiedWhen: {
        allFacts: ["old-accident-public-version-known"]
      }
    }
  ],
  completion: {
    allMilestones: ["public-version-known"]
  },
  handoffs: [
    {
      id: "talk-with-elder",
      capability: "conversation",
      targetId: "elder-old-accident",
      goalIds: [
        "elder-willing-to-talk",
        "public-version-known"
      ]
    }
  ],
  onComplete: [
    {
      id: "record-public-version-learned",
      eventType: "STORY_FACT_RECORDED",
      payload: {
        factId: "village-elder-topic-completed"
      }
    }
  ],
  transitions: [
    {
      id: "continue-to-x-interruption",
      to: "village-x-limits-investigation"
    }
  ],
  completesStage: false,
  terminal: false,
  endingId: null
}
```

### 8.2 必填与可选字段

| 字段 | 必填 | 约定 |
| --- | --- | --- |
| `id` | 是 | 运行时永久 ID，使用“阶段-剧情动作”的 kebab-case |
| `sourceRef` | 否 | 对应内容文档中的 P00、V11、O07 等编辑编号；不参与运行 |
| `stageId` | 是 | 所属阶段，例如 `prologue`、`village`、`old-house` |
| `revision` | 是 | Node 语义版本，正整数 |
| `intent` | 是 | 一句话说明这一段希望发生什么 |
| `enterWhen` | 否 | 进入前需要成立的事实；省略表示无额外条件 |
| `milestones` | 是 | 一个或多个稳定剧情里程碑；每项写结果，不写实现步骤 |
| `completion` | 是 | 哪些里程碑满足后 Node 才完成 |
| `handoffs` | 否 | 需要探索、对话或小游戏协助时填写 |
| `onComplete` | 否 | Node 首次完成后请求提交的状态事件；省略视为空数组 |
| `transitions` | 是 | 后继 Node 列表；终局 Node 可以为空数组 |
| `completesStage` | 是 | 本 Node 首次完成时是否同时完成 `stageId` 对应阶段 |
| `terminal` | 是 | 是否为剧情终点 |
| `endingId` | 条件必填 | `terminal: true` 时必须填写稳定结局 ID；其他 Node 为 `null` |

`P00`、`V11`、`O07` 只是 `剧情Node推进.md` 的编辑索引，不作为存档中的运行时 ID。运行时使用 `prologue-wake`、`village-elder-old-accident` 这类稳定 ID，原编号可放在 `sourceRef` 里追溯。

每个 `milestones` 项固定包含 `id`、`intent` 和 `satisfiedWhen`，需要在首次达成时结算效果的里程碑可增加 `onReach`。`onReach` 与 `onComplete` 使用相同的状态事件格式；省略时视为空数组。

`handoffs.capability` 与运行时命令一一对应：`exploration` 生成 `REQUEST_EXPLORATION`，`conversation` 生成 `REQUEST_CONVERSATION`，`minigame` 生成 `REQUEST_MINIGAME`。未登记的 capability 必须报错，不能当作普通剧情跳过。

每个 handoff 固定包含 `id`、`capability`、`targetId` 和 `goalIds`，可选 `startWhen`。省略 `startWhen` 表示进入 Node 后即可发出命令；填写后，只有条件成立且目标尚未完成时才能发出。这样同一 Node 可以表达“先看见白灯，再开始听小 X 解释”，又不需要把一句连续剧情拆成多个 Node。

### 8.3 条件格式

V1 条件只组合事实和里程碑，不允许在 Node 中写任意 JavaScript 函数：

```js
{
  allFacts: ["fact-a", "fact-b"],
  anyFacts: ["fact-c", "fact-d"],
  noneFacts: ["fact-e"],
  allMilestones: ["milestone-a"],
  anyMilestones: ["milestone-b", "milestone-c"]
}
```

判断规则：

- `allFacts` 中的事实必须全部成立；
- `anyFacts` 只要有一个成立；
- `noneFacts` 中的事实必须全部不成立；
- `allMilestones` 中的里程碑必须全部完成；
- `anyMilestones` 中至少有一个里程碑完成；
- 同时写了多个字段时，各组条件必须同时满足；
- 省略某个字段表示不检查该组条件；
- `completion` 至少要通过 `allMilestones` 或 `anyMilestones` 引用一个本 Node 的里程碑。

### 8.4 转移规则

- Node 只在 `completion` 满足后判断 `transitions`；
- 无 `when` 的转移是默认转移，每个 Node 最多一个；
- 有条件转移时，先计算有 `when` 的分支，没有命中才用默认转移；
- 同时命中多个条件分支属于数据错误，不能按数组第一项偷偷选择；
- 非终局 Node 完成后若没有可用转移，返回 `STORY_NO_TRANSITION`；
- 终局 Node 必须设置 `terminal: true`，并令 `transitions` 为空。
- 终局 Node 必须提供 `endingId`；非终局 Node 的 `endingId` 必须为 `null`。
- Node 首次完成时把自身 ID 加入 `completedNodeIds`；`completesStage: true` 时同时把 `stageId` 加入 `completedStageIds` 并发出阶段完成通知。

### 8.5 什么可以改，什么不能靠改稿破坏

| 改动 | 是否需要增加 `revision` | 对旧存档的要求 |
| --- | --- | --- |
| 修改措辞、增删普通对白轮次 | 否 | 仍从最近里程碑恢复 |
| 改变界面分页、动画和按钮位置 | 否 | 与剧情检查点无关 |
| 新增不影响完成条件的可选内容 | 否 | 旧存档可继续 |
| 新增、删除或改名里程碑 | 是 | 必须提供明确迁移规则 |
| 修改进入条件、完成条件或转移 | 是 | 必须提供明确迁移规则 |
| 删除 Node 或改变 Node 的剧情含义 | 是 | 必须提供旧检查点迁移；不能猜测跳转 |

运行时 ID 发布后不改名。确实需要替换时，由存档/剧情负责人共同提供旧 ID 到新 ID 的显式迁移表；没有迁移表就返回版本不兼容错误。

### 8.6 剧情数据预检

新游戏或读档前必须先校验整份剧情数据，至少检查：

- Node、里程碑、handoff、转移、`onReach` 和 `onComplete` 的 ID 在各自范围内不重复；
- `completion`、`handoffs.goalIds` 和 `handoffs.startWhen` 引用的里程碑或事实真实存在；
- 转移目标 Node、事实 ID、物品 ID、地点 ID 和小游戏 ID 已登记；
- 非终局 Node 有可用出口，终局 Node 有 `endingId`；
- V1 起点能沿合法路径到达 V1 结束 Node。

发现错误时阻止进入游戏，界面显示剧情数据无法加载，控制台列出文件、Node ID 和具体字段。不能只跳过坏 Node 后继续。

## 9. 多轮闲聊的完整交接示例

以 V11 为例：

1. 剧情进入 `village-elder-old-accident`，提交当前检查点；
2. 剧情发出 `REQUEST_CONVERSATION`，只说明要让老人愿意谈旧事，并让玩家得知事故的公开版本；
3. 对话模块自行组织第一轮寒暄，未产生稳定事实，不调用剧情；
4. 第二轮后老人愿意继续谈，状态模块记录 `elder-old-topic-opened`，对话模块通过 `NPC_TALK_PROGRESS` 通知剧情；
5. 剧情记录 `elder-willing-to-talk` 里程碑，但继续停留在本 Node；
6. 玩家此时保存，存档记录已完成里程碑和对应的 `pendingCommands`；
7. 读档后重新发出同一 `commandId`，对话模块从自己的已存进度继续；
8. 后续谈话产生 `old-accident-public-version-known`，对话模块发出 `NPC_TALKED`；
9. 剧情确认 `public-version-known` 满足，首次完成 Node，提交 `onComplete` 并转入下一 Node。

把寒暄从两轮改成四轮不会影响 Node、存档或下一节点。真正影响推进的是稳定事实。

## 10. 幂等、并发和错误规则

### 10.1 不重复结算

- 相同 `requestId` 只能结算一次；
- 相同外部 `eventId` 只能应用一次；
- 同一 `commandId` 在刷新或读档后可以重发，但外部模块必须恢复原任务，不能重复创建奖励；
- 物品、选择和剧情事实等不可重复效果使用稳定 `onceKey`；
- Node 完成通知只在第一次从未完成变为完成时发出。

### 10.2 快速点击

协调器处理一次 `enterStory()` 期间应锁定当前剧情操作。重复点击产生的请求不能越过尚未提交的状态事务。锁定失败或收到过期 `actionId` 时返回错误，不推进 Node。

### 10.3 必须显式报错的情况

| 错误码 | 情况 | 处理 |
| --- | --- | --- |
| `STORY_INVALID_REQUEST` | 请求缺字段或类型不合法 | 保持旧检查点，显示可理解提示 |
| `STORY_INVALID_NODE_DATA` | 剧情数据预检失败 | 阻止进入游戏，报告文件、Node 和字段 |
| `STORY_UNKNOWN_NODE` | `nodeId` 不存在 | 停止推进，提供返回主菜单入口 |
| `STORY_REVISION_MISMATCH` | Node 版本不兼容且没有迁移 | 保留存档，提示版本不兼容 |
| `STORY_INVALID_ACTION` | `actionId` 不属于当前可执行操作 | 忽略操作并报告错误 |
| `STORY_ENTRY_CONDITION_FAILED` | 请求进入的 Node 不满足 `enterWhen` | 保持原检查点，列出缺少或冲突的事实 |
| `STORY_STALE_EXTERNAL_EVENT` | 外部结果对应的命令已结束或不属于当前 Node | 不提交结果，记录命令与事件 ID |
| `STORY_EXTERNAL_RESULT_INCOMPLETE` | 外部模块报告成功，但约定的必要事实仍未成立 | 保留原命令，指出缺少的事实 |
| `STORY_AMBIGUOUS_TRANSITION` | 同时命中多个后继分支 | 停止推进，记录命中的分支 ID |
| `STORY_NO_TRANSITION` | 非终局 Node 完成后无可用出口 | 停止推进，提供安全返回入口 |
| `STORY_COMMIT_FAILED` | 状态事件或检查点提交失败 | 不显示新内容，不分发命令和成功通知 |
| `STORY_EXTERNAL_FAILED` | 对话、探索或小游戏失败 | 保持当前 Node，给出重试或退出方式 |

`StoryResponse.error` 的最低格式：

```js
{
  errorCode: "STORY_UNKNOWN_NODE",
  userMessage: "当前剧情无法读取。你可以重试或返回主菜单。",
  developerMessage: "Unknown nodeId: village-missing-node",
  recoveryActions: ["retry", "return-menu"]
}
```

界面显示 `userMessage`，控制台记录带模块名的 `developerMessage`。禁止空 `catch`、白屏、自动跳到别的 Node，或失败后仍返回成功状态。

## 11. 与现有团队约定的衔接

本文件沿用 `team-interface-contract-v1.md` 的以下规则：统一 ID、状态模块统一修改状态、存档模块统一读写本地存储、错误必须可见。

`需求文档v1.md` 的 R07 写有“每个节点至少包含唯一 ID、文本、可选目标节点、进入条件和状态效果”。本文把其中的“文本”落实为可包含多个块的 `presentation`，不设单一 `text` 必填字段；人物对话则改用目标式 handoff。这样仍满足内容与渲染分离，也不会把一个 Node 锁死成一句话。

现有团队约定第 4.3 节的示例在处理 `MAP_PUZZLE_COMPLETED` 时直接把 `currentNodeId` 设为 `old-house-arrival`。正式联调时必须删除这一步，改为：

1. 状态模块只记录地图完成、完整地图和相关状态；
2. 协调器把更新后的事实与 `MAP_PUZZLE_COMPLETED` 交给 `enterStory()`；
3. 剧情模块决定是否进入 `old-house-arrival`，并通过 `commit.checkpoint` 提交。

否则状态模块和剧情模块会同时掌握剧情跳转权，产生无法判断来源的错线 Bug。涉及剧情边界时，以本文为准；团队公共约定应在联调前同步更新。

`NPC_TALK_PROGRESS`、外部取消/失败事件、`CLUE_RECORDED`、剧情命令和剧情通知目前未列入团队公共事件表，也必须在联调前按本文补充。补充只登记名称和载荷，不得另造第二套同义事件。

## 12. 双重审核记录

## 13. 联调验收清单

### 接口结构

- [ ] 所有进入剧情的路径都调用 `enterStory()`；
- [ ] 外部模块没有直接传入或修改下一 Node；
- [ ] 状态先提交外部结果，再生成剧情上下文；
- [ ] 剧情返回的检查点和状态事件按事务提交；
- [ ] 提交失败时不会显示推进后的内容。

### Node 数据

- [ ] 每个 Node 有稳定 `id`、`stageId`、`revision` 和 `intent`；
- [ ] 每个 Node 至少有一个里程碑，完成条件引用真实里程碑；
- [ ] 里程碑描述剧情结果，不描述点击次数或文本序号；
- [ ] 非终局 Node 有且只有一个确定出口，或有互斥分支和一个默认出口；
- [ ] 阶段收束 Node 正确设置 `completesStage`，终局 Node 正确设置 `endingId`；
- [ ] P00、V11 等编号只作 `sourceRef`，不进入存档。

### 对话与外部模块

- [ ] 对话命令只写参与者、目标和完成事实；
- [ ] 具体台词、轮数和展示归对话模块；
- [ ] 多轮谈话可多次报告进展，剧情不会因一次 `NPC_TALK_PROGRESS` 自动结束；
- [ ] 取消和失败都有事件，剧情不会把失败当完成；
- [ ] 读档会恢复原 `commandId`，不会重复发奖。

### 容错

- [ ] 存档只依赖 Node 和里程碑 ID，不依赖句子序号；
- [ ] 改对白轮数不需要迁移存档；
- [ ] 修改里程碑或转移时增加 `revision` 并提供迁移；
- [ ] 重复请求、重复事件和快速点击不会重复结算；
- [ ] 未知 Node、冲突分支、缺少出口和提交失败均有可见错误。

以上检查用于验收接口实现，不表示本文档仍缺少字段。团队确认采用本约定后，把文档状态改为 `V1.0 已冻结`。后续可以增加新的 Node、事实 ID 和已登记事件类型，但不得改变 V1 字段的含义；确需不兼容修改时启用新的主版本。
